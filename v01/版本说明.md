# v01 基线版本说明

## 版本定位

`v01` 是当前 Tokenizer → PretrainDataset → Transformer → Train 全流程的基线快照。本版本只归档，不修改源代码，后续版本均从对应上一版本复制后再调整。

## Tokenizer

### `train_iterator` → 数据规模依赖手工记录

- 问题：`tokenizer_trianed.py` 中每个 JSONL 的总记录数由常量手工填写；文件变化后可能抽样不完整或提前结束。
- 类型：边界问题、可维护性问题。
- 后续目标：由预处理结果或索引文件提供可靠记录数，并校验实际读取数量。

### `record_to_texts` → 一个 tokenizer 混合多个训练阶段语料

- 问题：Tokenizer 同时抽取预训练、SFT、DPO 和 RL 数据。可行但会使词频分布受后训练数据影响，且各来源配比依赖手工常量。
- 类型：数据设计问题。
- 后续目标：明确各语料权重，输出每类文本和 token 占比统计。

### Tokenizer 配置 → 上下文长度不一致

- 问题：Tokenizer 的 `model_max_length` 是 32768，当前模型配置的 `max_sequence_length` 是 2048。
- 类型：配置一致性问题。
- 后续目标：使用统一配置源，并区分 tokenizer 理论上限和当前模型训练上限。

## PretrainDataset

### `PretrainDataset.__getitem__` → 长文本尾部被丢弃

- 问题：每条 JSONL 只生成一个固定长度样本，超过 `max_sequence_length` 的 token 被截断。
- 类型：训练数据逻辑问题、数据利用率问题。
- 后续目标：将文档以 EOS 分隔后组成连续 token 流，再切分成固定长度训练块。

### `PretrainDataset.__getitem__` → 短文本产生大量 padding

- 问题：每条文档独立补齐至固定长度，短文本会浪费 Attention 计算。
- 类型：性能问题。
- 后续目标：使用 token packing，减少 PAD 比例，同时保留文档 EOS 边界。

### `PretrainDataset._build_line_offsets` → 每次启动扫描全部 JSONL

- 问题：初始化时扫描完整数据文件并保存 Python 整数偏移；数据规模扩大后启动慢且占用内存。
- 类型：性能问题。
- 后续目标：持久化索引，或预先生成可内存映射的 token 数据文件。

### `PretrainDataset.__getitem__` → 单条坏数据中断训练

- 问题：非法 JSON、非法 UTF-8、缺少 `text` 都会直接抛异常。
- 类型：边界处理问题。
- 后续目标：训练前执行数据校验并生成错误报告，训练过程只消费已验证数据。

## Transformer 模型

### `ZeroTransformerConfig.hidden_size_per_head` → 派生值不会随实例参数更新

- 问题：该字段在类定义时通过默认 `hidden_size // num_heads` 计算；自定义 hidden size 或 head 数时可能沿用旧值。
- 类型：严重逻辑错误。
- 后续目标：在配置初始化后动态计算，并校验 `hidden_size % num_heads == 0`。

### `ZeroTransformerModel` → embedding 维度缺少约束

- 问题：`embeed_size` 可以与 `hidden_size` 不同，但后续 LayerNorm 和残差路径要求维度一致。
- 类型：边界问题、配置错误。
- 后续目标：统一字段命名为 `embedding_size`，并在构造模型前校验维度。

### `ZeroTransformerSingleHead` → 每个 head、每层重复保存完整 mask

- 问题：默认 12 层 × 8 heads 会创建 96 份 2048×2048 mask，并写入 checkpoint。
- 类型：严重显存和存储性能问题。
- 后续目标：每层共享一份布尔 mask，或改用 PyTorch SDPA 的 `is_causal=True`。

### `ZeroTransformerMultiHead.forward` → Python 循环执行独立注意力头

- 问题：每个 head 独立执行 Q/K/V Linear，再拼接结果，GPU kernel 碎片化严重。
- 类型：性能问题。
- 后续目标：合并 QKV 投影并 reshape 为多头，优先采用 `scaled_dot_product_attention`。

### `ZeroTransformerModel.forward` → 返回 logits 形状不稳定

- 问题：不传 target 时返回 `[B,T,V]`；传 target 后覆盖 logits 并返回 `[B*T,V]`。
- 类型：接口逻辑问题。
- 后续目标：始终返回三维 logits，loss 内部只使用临时展平结果。

### 配置开关 → 声明后未生效

- 问题：`activation_fn`、`tie_embeddings`、`tie_projection` 没有控制实际模型行为。
- 类型：配置逻辑问题。
- 后续目标：实现有效开关或删除无效字段，避免产生错误预期。

## 训练脚本

### 模型导入 → 类名不存在

- 问题：`train_pretrain.py` 导入 `ZeroTransformer`，模型文件实际定义的是 `ZeroTransformerModel`。
- 类型：阻塞性错误。
- 修改后目标：统一导入和实例化名称，训练脚本可以启动。

### `PretrainDataset` 构造 → 参数接口不匹配

- 问题：传入 `data_dir` 和 `tokenizer_path`，但 Dataset 需要 `data_path`、tokenizer 对象和最大序列长度。
- 类型：阻塞性错误。
- 修改后目标：显式加载 tokenizer，并传入具体 JSONL 文件。

### `train` / `evl` → `F` 未导入

- 问题：调用 `F.cross_entropy`，但没有导入 `torch.nn.functional as F`。
- 类型：阻塞性错误。
- 修改后目标：如果由模型计算 loss，则移除重复 loss；否则补充正确导入和 shape 处理。

### `train` / `evl` → 错误处理模型返回值

- 问题：模型返回 `(logits, loss)`，脚本将整个 tuple 当成 logits；同时 `[B,T,V]` 不能按当前方式直接与 `[B,T]` 计算交叉熵。
- 类型：阻塞性逻辑错误。
- 修改后目标：训练和验证统一调用 `model(x, y)`，使用模型返回的 loss。

### 脚本顶层执行 → 无入口保护

- 问题：导入训练脚本就会加载数据并开始训练，不利于测试和多进程 DataLoader。
- 类型：可维护性和边界问题。
- 修改后目标：封装 `main()` 并使用 `if __name__ == "__main__":`。

### 训练工程能力 → 无恢复机制

- 问题：缺少 checkpoint、断点恢复、scheduler、warmup、梯度累积、AMP 和 NaN 检查。
- 类型：稳定性和性能问题。
- 修改后目标：先增加 checkpoint 与恢复，再逐步加入训练优化能力。

## 安全性

当前源码未发现明显的命令注入、任意代码执行或不可信反序列化问题。后续加载 checkpoint 时应优先使用安全权重格式，并只加载可信来源文件。

## v01 整体状态

- Tokenizer：已具备训练、保存和模板测试能力。
- Dataset：能生成 next-token 样本，但数据利用率和大规模性能仍需优化。
- Model：结构完整，但配置派生值、mask 内存和输出接口存在问题。
- Train：存在多个阻塞性错误，当前不能直接启动完整训练。
