# v01 基线版本说明

## 版本定位

`v01` 是当前 Tokenizer → PretrainDataset → Transformer → Train 全流程的基线快照。本版本只归档，不修改源代码。下面每项均按“问题、类型、具体修改方式、修改后效果”记录，后续实际修改版本应注明最终采用了哪一种方案。

## Tokenizer

### `train_iterator` → 数据规模依赖手工记录

- **问题**：`tokenizer_trianed.py` 中每个 JSONL 的总记录数由常量手工填写；文件变化后可能抽样不完整或提前结束。
- **类型**：边界问题、可维护性问题。
- **具体修改方式**：
  1. 将 `DATA_SOURCES` 中的三元组 `(file_path, total_records, max_records)` 改为只保存路径和抽样上限，不再由人工维护 `total_records`。
  2. 新增 `count_jsonl_records(file_path)`，在首次处理数据时以二进制方式逐行统计非空记录数，并把结果及文件大小、修改时间写入索引文件。
  3. 再次启动时先核对文件大小和修改时间；一致则读取索引中的记录数，不一致则重新统计。
  4. `train_iterator` 使用索引提供的实际记录数计算均匀抽样位置，并在结束后校验已扫描行数和已选样本数；不一致时抛出包含文件路径的明确错误。
- **修改后效果**：数据文件增删记录后不需要同步修改源码，均匀抽样范围与实际文件一致，同时避免每次启动都重复统计完整文件。

### `record_to_texts` → 一个 tokenizer 混合多个训练阶段语料

- **问题**：Tokenizer 同时抽取预训练、SFT、DPO 和 RL 数据。可行但会使词频分布受后训练数据影响，且各来源配比依赖手工常量。
- **类型**：数据设计问题。
- **具体修改方式**：
  1. 为每类数据源增加 `source_type`、`sample_limit` 和 `weight` 配置，不再只依靠列表顺序和固定抽样数量表达比例。
  2. 把 `record_to_texts` 拆成 `extract_pretrain_text`、`extract_sft_text`、`extract_preference_text` 和 `extract_agent_text`，每个函数只处理一种明确的数据结构。
  3. `train_iterator` 按配置调用对应提取函数，并记录每类语料实际输出的文档数、字符数和 token 数。
  4. 训练结束后将语料占比统计写入独立报告，确认各来源没有因一条记录产生多个文本而意外放大权重。
- **修改后效果**：Tokenizer 语料组成可以审计和复现，各训练阶段数据的占比明确，调整采样权重时无需改动文本解析逻辑。

### Tokenizer 配置 → 上下文长度不一致

- **问题**：Tokenizer 的 `model_max_length` 是 32768，当前模型配置的 `max_sequence_length` 是 2048。
- **类型**：配置一致性问题。
- **具体修改方式**：
  1. 明确区分 `tokenizer_model_max_length` 与本次训练使用的 `max_sequence_length`：前者表示 tokenizer 允许的理论上限，后者表示模型位置编码和训练样本的真实上限。
  2. 将模型训练长度放入统一配置，由 Dataset 和 `ZeroTransformerConfig` 读取同一个值，禁止在多个文件中分别写死 `2048`。
  3. 加载 tokenizer 后校验 `config.max_sequence_length <= tokenizer.model_max_length`；超出时在训练开始前直接报错。
  4. 保存模型时把真实上下文长度写入模型配置，推理端优先读取模型配置，而不是误用 tokenizer 的 32768 作为当前模型能力。
- **修改后效果**：Tokenizer、Dataset、模型和推理端对上下文长度的含义一致，不会生成超过位置编码范围的输入，也不会错误宣传模型支持 32768 上下文。

## PretrainDataset

### `PretrainDataset.__getitem__` → 长文本尾部被丢弃

- **问题**：每条 JSONL 只生成一个固定长度样本，超过 `max_sequence_length` 的 token 被截断。
- **类型**：训练数据逻辑问题、数据利用率问题。
- **具体修改方式**：
  1. 不再让“一行 JSONL”等于“一个训练样本”；先逐文档 tokenize，并在每个文档末尾追加 EOS。
  2. 新增预处理步骤，把所有 token 写入连续的二进制 token 文件，同时记录文档边界和总 token 数。
  3. Dataset 的长度改为 `可用 token 数 // (max_sequence_length + 1)`，`__getitem__` 根据索引读取连续的 `max_sequence_length + 1` 个 token。
  4. 使用前 `max_sequence_length` 个 token 作为 `input_ids`，后移一位的同长度 token 作为 `labels`，不再截掉长文档剩余部分。
  5. 如果必须保持在线 tokenize，则建立“文档行号、文档内 chunk 起点”的样本索引，使一篇长文档产生多个样本。
- **修改后效果**：长文档全部 token 都能参与训练，input/label 的 next-token 对齐清晰，样本数量由 token 总量决定而不是 JSONL 行数决定。

### `PretrainDataset.__getitem__` → 短文本产生大量 padding

- **问题**：每条文档独立补齐至固定长度，短文本会浪费 Attention 计算。
- **类型**：性能问题。
- **具体修改方式**：
  1. 与上一项共用连续 token 流方案，将多个短文档通过 EOS 串联后再切成固定长度 chunk。
  2. 保留 EOS 作为文档边界，确保模型能学习文档结束；base 预训练允许下一个文档 token 出现在 EOS 之后。
  3. 只对整个语料最后不足一个 chunk 的尾段选择“丢弃”或“补 PAD”，而不是对每篇文档分别补齐。
  4. 若尾段补 PAD，则将对应 label 设置为 `-100`，并让 loss 显式使用 `ignore_index=-100`。
  5. 新增有效 token 比例统计，验证每批 `non_pad_tokens / all_tokens` 接近 1。
- **修改后效果**：绝大多数计算用于真实 token，显存和训练时间不再被大量 PAD 消耗，同时文档边界仍由 EOS 明确保留。

### `PretrainDataset._build_line_offsets` → 每次启动扫描全部 JSONL

- **问题**：初始化时扫描完整数据文件并保存 Python 整数偏移；数据规模扩大后启动慢且占用内存。
- **类型**：性能问题。
- **具体修改方式**：
  1. 如果继续按行随机读取，则把字节偏移写入固定宽度的 `.idx` 文件，例如使用 64 位无符号整数，而不是长期保存在 Python `list[int]`。
  2. 索引头记录原数据文件的大小、修改时间和记录数；Dataset 初始化时先校验这些元数据。
  3. 通过 `numpy.memmap` 或同类内存映射按需读取偏移，避免一次把全部 Python 整数加载到内存。
  4. 如果采用预 token 化方案，则删除 `_build_line_offsets`，改为直接内存映射 token 文件，并通过固定 chunk 长度计算位置。
- **修改后效果**：重复启动不再扫描完整 JSONL，索引内存占用从大量 Python 对象降为紧凑的固定宽度整数；采用 token 文件后可完全移除行偏移逻辑。

### `PretrainDataset.__getitem__` → 单条坏数据中断训练

- **问题**：非法 JSON、非法 UTF-8、缺少 `text` 都会直接抛异常。
- **类型**：边界处理问题。
- **具体修改方式**：
  1. 新增独立数据校验或预处理阶段，逐行捕获 `UnicodeDecodeError`、`JSONDecodeError`、字段缺失和空文本。
  2. 将坏记录的文件名、行号、错误类型和截断后的内容摘要写入错误报告，不把原始完整敏感文本写入日志。
  3. 对错误记录执行跳过并计数；当错误比例超过配置阈值时终止预处理，防止在数据整体损坏时静默继续。
  4. 训练 Dataset 只读取预处理成功的 token 文件或有效记录索引，因此 `__getitem__` 不再承担清洗职责。
- **修改后效果**：少量坏数据不会在训练中途导致作业终止，数据质量问题在训练前可见、可统计；严重损坏仍会通过阈值检查阻止训练。

## Transformer 模型

### `ZeroTransformerConfig.hidden_size_per_head` → 派生值不会随实例参数更新

- **问题**：该字段在类定义时通过默认 `hidden_size // num_heads` 计算；自定义 hidden size 或 head 数时可能沿用旧值。
- **类型**：严重逻辑错误。
- **具体修改方式**：
  1. 删除 `hidden_size_per_head` 的可配置默认表达式，优先将其改为只读派生属性 `head_dim`。
  2. 在 `ZeroTransformerConfig.__post_init__` 中校验 `num_heads > 0`、`hidden_size > 0` 和 `hidden_size % num_heads == 0`。
  3. `head_dim` 每次通过 `hidden_size // num_heads` 计算；如果为了兼容旧配置保留字段，则默认设为 `None`，初始化后赋值并拒绝不一致的显式值。
  4. 所有 Attention Linear 和 reshape 只读取 `config.head_dim`，不在其他类中重复计算。
- **修改后效果**：修改 hidden size 或 head 数后，每头维度总是同步更新；非法维度在模型创建时被明确拒绝，不会到矩阵乘法阶段才报 shape 错误。

### `ZeroTransformerModel` → embedding 维度缺少约束

- **问题**：`embeed_size` 可以与 `hidden_size` 不同，但后续 LayerNorm 和残差路径要求维度一致。
- **类型**：边界问题、配置错误。
- **具体修改方式**：
  1. 将拼写错误的 `embeed_size` 重命名为 `embedding_size`；为旧配置提供一次兼容转换，随后移除旧字段。
  2. 当前架构不包含输入投影，因此最简单方案是删除独立的 `embedding_size` 配置，token embedding 和 position embedding 都直接使用 `hidden_size`。
  3. 如果确实需要二者不同，则在 embedding 求和后新增 `input_projection = nn.Linear(embedding_size, hidden_size, bias=False)`，再进入 Transformer Block。
  4. 位置 embedding 与 token embedding 必须保持相同维度；配置初始化时校验相关字段为正数。
- **修改后效果**：默认模型只有一个隐藏维度来源，不会在 LayerNorm 或残差加法处出现维度错误；扩展为不同 embedding 维度时也有明确投影路径。

### `ZeroTransformerSingleHead` → 每个 head、每层重复保存完整 mask

- **问题**：默认 12 层 × 8 heads 会创建 96 份 2048×2048 mask，并写入 checkpoint。
- **类型**：严重显存和存储性能问题。
- **具体修改方式**：
  1. 首选删除 `ZeroTransformerSingleHead` 中的 `attention_mask` buffer，并在合并多头后调用 `torch.nn.functional.scaled_dot_product_attention(..., is_causal=True)`。
  2. `is_causal=True` 由底层实现生成或融合因果约束，不再为每个 head 保存二维矩阵。
  3. 如果运行环境不支持 SDPA，则把一份布尔下三角 mask 注册在 `ZeroTransformerMultiHead` 或模型层级，并设置 `persistent=False`，所有 head 共享切片。
  4. forward 开始时校验 `sequence_length <= max_sequence_length`，避免 mask 切片不足产生隐式错误。
- **修改后效果**：去除 96 份重复 mask，降低显存、设备传输和 checkpoint 体积；因果注意力语义保持不变。

### `ZeroTransformerMultiHead.forward` → Python 循环执行独立注意力头

- **问题**：每个 head 独立执行 Q/K/V Linear，再拼接结果，GPU kernel 碎片化严重。
- **类型**：性能问题。
- **具体修改方式**：
  1. 删除 `ModuleList` 中多个 `ZeroTransformerSingleHead`，在 `ZeroTransformerMultiHead` 中新增一个 `qkv_projection = nn.Linear(hidden_size, 3 * hidden_size)`。
  2. forward 一次得到 QKV 后拆分，并 reshape/transpose 为 `[batch, num_heads, sequence, head_dim]`。
  3. 调用 `scaled_dot_product_attention(q, k, v, dropout_p=..., is_causal=True)` 完成所有 head 的注意力。
  4. 把输出转回 `[batch, sequence, hidden_size]`，再经过 `output_projection` 和 residual dropout。
  5. 添加 shape 断言和小张量等价性测试，对比旧实现与新实现关闭 dropout 时的输出尺寸和因果遮挡行为。
- **修改后效果**：QKV 投影和 Attention 由少量大 kernel 完成，可利用 SDPA 的高效后端，显著减少 Python 循环、kernel 启动和中间张量开销。

### `ZeroTransformerModel.forward` → 返回 logits 形状不稳定

- **问题**：不传 target 时返回 `[B,T,V]`；传 target 后覆盖 logits 并返回 `[B*T,V]`。
- **类型**：接口逻辑问题。
- **具体修改方式**：
  1. 保留 `logits = self.lm_head(x)` 的三维结果，不再把展平值重新赋给 `logits`。
  2. 计算 loss 时使用局部变量 `flat_logits = logits.reshape(-1, vocab_size)` 和 `flat_targets = targets.reshape(-1)`。
  3. 交叉熵显式设置 `ignore_index=-100`，与 Dataset 的 PAD label 约定保持一致。
  4. forward 无论是否传 target，都统一返回 `(logits, loss)`；未传 target 时 `loss=None`。
  5. 添加测试分别覆盖有无 target，两种情况下都断言 logits 为 `[B,T,V]`。
- **修改后效果**：训练、验证和推理获得稳定的模型接口；loss 的内部 shape 处理不会改变调用方收到的 logits。

### 配置开关 → 声明后未生效

- **问题**：`activation_fn`、`tie_embeddings`、`tie_projection` 没有控制实际模型行为。
- **类型**：配置逻辑问题。
- **具体修改方式**：
  1. 为 `activation_fn` 建立受控映射，例如 `{"relu": nn.ReLU, "gelu": nn.GELU, "silu": nn.SiLU}`；`ZeroTransformerFNN.__init__` 根据配置实例化激活函数，未知名称立即抛出 `ValueError`，不允许静默回退。
  2. 为 `tie_embeddings` 实现真实分支：`True` 时将 `lm_head` 设为无 bias，并在权重初始化完成后执行 `self.lm_head.weight = self.token_embedding_table.weight`；同时校验 hidden size 与 embedding 输出维度一致。`False` 时保留独立输出权重。
  3. 先明确 `tie_projection` 的语义。当前架构不存在自然可共享且 shape 一致的投影矩阵，因此不应保留含义模糊的开关；应从配置中删除该字段，并在版本说明中记录破坏性配置变更。如果未来定义为 Q/K/V 权重共享，则应另建名称明确的 `share_qkv_weights`，并实现对应模块结构和测试。
  4. 增加配置测试：逐个切换开关，验证模块类型、Parameter 对象是否共享、参数量是否按预期变化；无测试覆盖的配置字段不得保留。
- **修改后效果**：每个保留的配置项都能改变真实模型结构或行为；无明确含义的开关被删除，配置文件不会再给使用者造成“已启用但实际无效”的错误预期。

## 训练脚本

### 模型导入 → 类名不存在

- **问题**：`train_pretrain.py` 导入 `ZeroTransformer`，模型文件实际定义的是 `ZeroTransformerModel`。
- **类型**：阻塞性错误。
- **具体修改方式**：
  1. 将导入改为 `from zerotransformer import ZeroTransformerConfig, ZeroTransformerModel`。
  2. 将实例化改为 `model = ZeroTransformerModel(config)`，删除所有不存在的 `ZeroTransformer` 引用。
  3. 如果希望对外类名更短，应在模型文件中统一重命名类及其所有引用，而不是只修改训练脚本的一端。
  4. 增加仅导入训练模块和创建小模型的 smoke test，确保类名重构不会再次断开接口。
- **修改后效果**：训练入口可以成功导入并实例化实际模型类，模型命名在定义端和调用端保持一致。

### `PretrainDataset` 构造 → 参数接口不匹配

- **问题**：传入 `data_dir` 和 `tokenizer_path`，但 Dataset 需要 `data_path`、tokenizer 对象和最大序列长度。
- **类型**：阻塞性错误。
- **具体修改方式**：
  1. 在训练入口先调用 `AutoTokenizer.from_pretrained(tokenizer_directory)` 得到 tokenizer 对象。
  2. 使用具体 JSONL 路径构造 `PretrainDataset(data_path=..., tokenizer=..., max_sequence_length=config.max_sequence_length)`，不能把目录当成数据文件。
  3. 在启动阶段检查数据文件和 tokenizer 目录是否存在，并检查 `len(tokenizer) == config.vocab_size`；若不一致则使用 tokenizer 长度生成配置或明确报错。
  4. 将路径改为命令行或配置参数，移除散落在脚本中的绝对路径。
- **修改后效果**：Dataset 获得正确类型和含义的参数，词表大小与模型输出层一致，脚本可以在不同目录和数据文件间复用。

### `train` / `evl` → `F` 未导入

- **问题**：调用 `F.cross_entropy`，但没有导入 `torch.nn.functional as F`。
- **类型**：阻塞性错误。
- **具体修改方式**：
  1. 当前模型已经支持传入 target 并返回 loss，因此训练脚本应删除重复的 `F.cross_entropy` 调用，而不是再维护第二套 loss 逻辑。
  2. 训练和验证统一写为 `logits, loss = model(input_ids, labels)`，并检查 `loss is not None`。
  3. 只有在决定把 loss 完全移出模型时，才导入 `torch.nn.functional as F`，并统一使用 `logits.reshape(-1, vocab_size)`、`labels.reshape(-1)` 和 `ignore_index=-100`。
  4. 两种方案只能选择一种，避免模型和训练脚本各自计算 loss 后行为不一致。
- **修改后效果**：不会再出现未定义名称；next-token loss 只有一个权威实现，训练和验证使用完全一致的 padding 忽略规则。

### `train` / `evl` → 错误处理模型返回值

- **问题**：模型返回 `(logits, loss)`，脚本将整个 tuple 当成 logits；同时 `[B,T,V]` 不能按当前方式直接与 `[B,T]` 计算交叉熵。
- **类型**：阻塞性逻辑错误。
- **具体修改方式**：
  1. 将 `logits = model(x)` 改为 `logits, loss = model(x, y)`，不得把 tuple 传给张量运算。
  2. loss 由模型内部按词表维度展平计算，训练脚本只负责检查有限值、反向传播和记录标量。
  3. 验证阶段使用相同调用方式并放在 `torch.no_grad()` 或 `torch.inference_mode()` 中。
  4. 增加单 batch 测试，断言 logits shape 为 `[B,T,V]`、loss 为零维有限 Tensor，并完成一次 `loss.backward()`。
- **修改后效果**：训练和验证能够正确消费模型返回值，交叉熵维度与 next-token labels 对齐，单步反向传播可以运行。

### 脚本顶层执行 → 无入口保护

- **问题**：导入训练脚本就会加载数据并开始训练，不利于测试和多进程 DataLoader。
- **类型**：可维护性和边界问题。
- **具体修改方式**：
  1. 把配置解析、tokenizer/Dataset/DataLoader 创建、模型创建和 epoch 循环封装进 `main()`。
  2. 文件末尾只通过 `if __name__ == "__main__": main()` 启动训练。
  3. 把 `train_one_epoch` 和 `evaluate` 保留为无顶层副作用的独立函数，使测试可以直接导入。
  4. 多进程 DataLoader 所需对象在 `main()` 内创建，避免子进程重新导入模块时重复启动训练。
- **修改后效果**：导入训练函数不会触发长任务，单元测试和多进程数据加载可以安全使用训练模块。

### 训练工程能力 → 无恢复机制

- **问题**：缺少 checkpoint、断点恢复、scheduler、warmup、梯度累积、AMP 和 NaN 检查。
- **类型**：稳定性和性能问题。
- **具体修改方式**：
  1. 第一阶段先实现 checkpoint：按固定 step 保存模型、优化器、scheduler、当前 epoch/step、随机数状态和训练配置；写入临时文件后原子重命名，防止中断产生半个 checkpoint。
  2. 启动时增加 `resume_from` 参数，恢复所有状态并从保存 step 继续，而不是只加载模型权重后重新计数。
  3. 第二阶段加入 warmup + 学习率衰减 scheduler，每次 optimizer step 后更新；梯度累积时只在累积边界执行 optimizer 和 scheduler。
  4. 根据硬件支持选择 BF16 或 FP16；FP16 使用 GradScaler，CPU 或不兼容 GPU 保持 FP32。
  5. backward 前后检查 loss 和梯度是否有限，异常时跳过更新、记录 batch/step，并在连续异常达到阈值后终止。
  6. 为 checkpoint 恢复做短程一致性测试：连续训练 N 步与中途保存恢复后的参数和 step 应在允许误差内一致。
- **修改后效果**：长期训练中断后可以准确续训，学习率和混合精度行为可控，NaN/Inf 不会静默污染全部参数。

## 安全性

### Checkpoint 加载 → 后续可能引入不可信反序列化

- **问题**：当前尚未实现 checkpoint 加载；后续若直接加载不可信 pickle 对象，可能执行恶意代码。
- **类型**：安全风险。
- **具体修改方式**：
  1. 模型权重优先使用 `safetensors`；训练状态若使用 `torch.load`，只加载本项目生成且来源可信的文件，并在可用版本中使用限制权重反序列化的选项。
  2. checkpoint 路径只能来自明确配置，不接受数据记录中的任意路径。
  3. 不把 PAT、环境变量、绝对私有数据路径或原始训练样本写入 checkpoint 和日志。
  4. Git 提交前继续通过 `.gitignore` 排除权重、日志、数据集和认证文件。
- **修改后效果**：恢复训练不会扩大到任意不可信对象执行，仓库和训练产物中不包含认证信息或原始私有数据。
